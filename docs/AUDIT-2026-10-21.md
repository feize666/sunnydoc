## 一、代码隐患

### 🔴 1.1 跨用户越权（IDOR）—— 已修复

**为什么值得单独说**：这是本轮唯一的**真实安全漏洞**，且与「最近几轮在改什么」无关 —— 它是被「按覆盖率找空白」这个流程挖出来的。

#### 缺陷 A：`POST /documents/{doc_id}/unpin` 缺少归属校验

- `POST /documents/{id}/pin` **有**校验（`store.get(doc_id, current_user["id"])`）
- `POST /documents/{id}/unpin` **没有** —— 直接 `store.set_pinned(doc_id, False)`
- 而 `store.set_pinned()` **只按 doc_id 改字段、不接收 user_id**，因此任何登录用户都能凭 id 取消**他人**文档的置顶

**实测证据**（两个无关用户 u1 / u2）：

```
① 前提：u1 置顶成功（pinned === true）        ✅ pin HTTP=200 pinned=true
② u2 调 u1 文档的 unpin                       ❌ HTTP=200 {"pinned":false}
③ u1 回读：置顶被篡改                         ❌ pinned=false  ← 跨租户写入
④ 对照：u2 调 pin（有校验）                    ✅ HTTP=404
```

第 ④ 条是关键：**同一资源的两个动词，一个有校验一个没有** —— 这证明是遗漏而非设计，也说明判据有区分度（不是恒真断言）。

#### 缺陷 B：`POST /folders/{folder_id}/pin` 与 `/unpin` 均无校验

同一类缺陷，且**两个动词都没有**校验。实测 u2 可置顶/取消置顶 u1 的文件夹（均返回 200）。

> 这正是项目 `MEMORY.md` 里早已记下的规则 —— **「同一资源多个动词，鉴权容易只写一个」** —— 但规则写在记忆里，代码里仍然漏了。说明这类问题**必须靠测试覆盖兜住，不能靠记忆**。

#### 修复

```python
# documents/unpin：补齐与 pin 一致的归属校验
if store.get(doc_id, current_user["id"]) is None:
    raise HTTPException(status_code=404, detail="文档不存在")
store.set_pinned(doc_id, False)

# folders/pin 与 folders/unpin：改用已有的 _require_folder_access
_require_folder_access(folder_id, current_user)
```

#### 防复发

新增 `web/scripts/verify_authz_idor.cjs`（**22 项断言，全绿**）。此前 `grep -rn "/pin|/unpin" web/scripts/` → **0 命中**，这就是缺陷存活的原因。

**对抗性验证 ×2**（回滚实现，判据必须精确失败）：

| 注入 | 结果 |
|---|---|
| 回滚文档 unpin 校验 | **精确失败 2 项**（返回 200 + 置顶被篡改） |
| 回滚文件夹 pin/unpin 校验 | **精确失败 2 项**（两个动词各自失败） |

两次失败项**互不重叠**，说明判据定位精确、没有虚假耦合。

### 🔴 1.2 登录接口无频率限制（暴力破解防护缺失）

**实测**：连续 12 次错误密码，**全部返回 401，总耗时 127ms**，无 429、无延迟递增、无锁定。

```
状态码=401,401,401,401,401,401,401,401,401,401,401,401  用时=127ms
```

**风险**：`_validate_new_password` 只要求 **6 位**最小长度，且无复杂度要求。在无节流的情况下，弱口令（如 `123456`）可被高速枚举。实测单次请求约 10ms，意味着**每分钟可尝试约 6000 次**。

**已做的正确部分**（值得肯定）：`login` 对「用户不存在」与「密码错误」返回**完全相同**的信息 `用户名或密码错误` —— 实测确认，防住了用户名枚举。

**修复建议**（需你决策，涉及产品策略）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 按 `username + 客户端 IP` 计数，连续失败 N 次后指数退避 / 临时锁定 | 需引入存储（进程内 dict 即可，与现有 `_REVOKED_TOKENS` 同风格） |
| B | 接入 `slowapi` 中间件，全局按 IP 限流 | 新增依赖；多实例部署需共享存储 |
| C | 仅提高密码下限至 8 位 + 复杂度校验 | 最轻，但**不解决**在线爆破 |

> ⚠️ 注意：`auth.py` 的吊销黑名单是**进程内内存**（`_REVOKED_TOKENS` / `_REVOKED_USERS`），重启即清空。注释已说明「JWT 本身 7 天过期，属可接受的折中」。但**多进程部署下这份黑名单不共享** —— 若将来起多个 uvicorn worker，登出/改密将只在其中一个 worker 生效。这是架构级注意事项，建议记入文档。

### 🔴 1.3 `/documents/import` 完全没有大小上限

**对比**：
- `/upload/attachment` → `MAX_ATTACHMENT_BYTES = 30MB`（超限 413）✅
- `/upload/image` → `MAX_IMAGE_BYTES = 10MB`（超限 413）✅
- **`/documents/import` → 函数体内除「是否为空」外无任何大小判断** ❌

代码只做了流式落盘（避免整读内存，这点是对的），但**没有累计字节数上限**。且全局也无 `Content-Length` 校验或请求体上限。

**风险**：一次性导入超大文件可打满磁盘 / 长时间占用 worker。

**修复建议**：在流式写入循环内累计字节数，超过上限（建议与附件对齐 30MB，或按需放宽到 100MB）即中止并清理临时文件：

```python
total = 0
while True:
    chunk = await file.read(1024 * 1024)
    if not chunk: break
    total += len(chunk)
    if total > MAX_IMPORT_BYTES:
        raise HTTPException(status_code=413, detail="文件过大")
    out.write(chunk)
```

### 🟡 1.4 `/media/{filename}` 未鉴权 —— 设计取舍，但需确认无敏感内容

**实测**：无 token 访问 `/api/v1/media/{hash}.png` → **200**，返回完整图片（360,637 字节）。

- **这是有意的**：图片要能被 `<img>` 直接加载（`<img>` 无法附加 `Authorization` 头），且分享页需要它。若加鉴权会直接弄坏图片显示与分享。
- **防护到位**：内容寻址（sha1 前 16 位）使文件名**不可枚举**，攻击者必须已知确切 hash 才能取到文件 —— 这实际上是一种 capability URL 设计。路径穿越也已封死（实测 4 种载荷全部 404）。
- **但需确认**：`/upload/attachment` 走的是**同一套 `/media/` 存储**。**当前实测 media 目录 2118 个文件全部是图片**（png/jpg/webp/gif/svg），无 PDF/docx 等文档类附件 —— 所以**当前无实际泄露**。

**建议**：
1. 若将来附件功能被使用（上传了 PDF 合同等），**这些附件将与图片一样可被无鉴权访问**（已知 hash 即可）。建议为附件单独设计带鉴权的下载端点，或至少输出审计日志。
2. `media_audit.py` 已有只读体检脚本，可定期核对文件类型分布。

### 🔴 2.1 代码块配色未针对本项目底色校准（影响最大）

**根因**：shiki 的两个主题都按**自己的底色**设计，而项目用 `!important` 强制改底：

```css
.md-body pre.shiki {
  /* 覆盖 shiki 行内背景 */
  background-color: var(--surface-2) !important;
}
```

- 浅色：`github-light` 为 `#ffffff` 设计 → 实际落在 `--surface-2` `#eef2f7`
- 深色：`one-dark-pro` 为 `#282c34` 设计 → 实际落在 `--surface-2` `#1e293b`

**实测不达标 token 数**（对全部 tokenColors 前景色逐一计算）：

| 主题底色 | 不达标 | 具体 token |
|---|---|---|
| 浅色 `#eef2f7`（当前） | **6/12** | `#6a737d`=4.28　`#22863a`=4.12　`#d73a49`=4.07　`#e36209`=3.10 |
| 浅色 `#ffffff`（还原 shiki） | 3/12 | `#e36209`=3.49 |
| 深色 `#1e293b`（当前） | **4/13** | `#5c6370`=2.42　`#BE5046`=3.08　`#7f848e`=3.90　`#f44747`=4.07 |
| 深色 `#282c34`（还原 shiki） | 5/13 | — |

**这也解释了浏览器实测里那一串 `# 图形化配置网卡` 提示**：那些是 Python 代码里的注释行，渲染为 `#6a737d`，在 `--surface-2` 上只有 **4.28**。

**修复建议**（推荐 shiki 原生 `colorReplacements`，不改 DOM 结构）：

```ts
  "#6a737d": "#5b6672",   // 4.28 → 5.21  注释（最常见）

  "#e36209": "#b1540a",   // 3.10 → 4.51  数字常量

// 深色 one-dark-pro

  "#7f848e": "#a6adb8",   // 3.90 → 6.47
  "#f44747": "#ff6b6b",   // 4.07 → 5.27
  "#BE5046": "#e06c75",   // 3.08 → 4.58
},
```

> 注：`#fafbfc` / `#f6f8fa` 两个极浅色是 shiki 用于**反色语境**（如 diff 删除行）的底色，在此处不构成实际文字，可忽略。
