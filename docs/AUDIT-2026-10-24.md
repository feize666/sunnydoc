## 二、🔴 最高优先级：超长文档渲染阻塞

### 实测（Playwright，真实点击文档树打开）

```
DOM 节点          17,372
正文文本          181,999 字符
内容高度          232,988px（≈233 米）
长任务            7 次
主线程总阻塞       868ms
最长单次阻塞       275ms
代码块 638 个      → 3.0 秒内全部高亮，而首屏可见 0 个
```

### DOM 增长曲线（证明「渐进渲染有效，但总成本没降」）

```
  2330ms    320 节点    24 代码块   ← 首屏
  2523ms   1759 节点   127 代码块   ← 100 块/批推进中
  3001ms   8614 节点   638 代码块   ← 638 个代码块已全部高亮完
  3602ms  11473 节点   638 代码块   ← 但 DOM 还在长
  4803ms  17372 节点   638 代码块   ← 才稳定
```

**判读**：已有渐进渲染（`renderProgressively`，100 块/批 + `requestIdleCallback`）
是**正确且生效**的 —— 节点确实分批增长。但它只把阻塞**摊开**，没有降低**总成本**：
最终仍渲染全部 17,372 节点，且 **638 个代码块在 3 秒内就被全部 shiki 高亮，
而首屏可见的代码块数是 0** —— 也就是说**绝大部分高亮是白做的**。

长任务集中在 4.2s 之后（275 / 86 / 126 / 92 / 99 / 93 / 102 ms），
说明瓶颈在**批次的样式计算与布局**，不在 JS 解析。

### 🔴 根因追查（4 轮实测，最终定位到 CPU profile）

| 轮次 | 假设 | 实测结果 | 结论 |
|---|---|---|---|
| 1 | 代码块全量高亮是主因 | 改「近视口优先」排序 → 638 块仍 3.6s 内全高亮 | ❌ 无效 |
| 2 | `offsetTop` 坐标系算错 | 改用 `getBoundingClientRect` → 仍无效 | 修正了 bug，但**不是主因** |
| 3 | 调度频率不够 | 加 `requestIdleCallback` 埋点 → **88 次调用、间隔仅 14–22ms** | ❌ 浏览器不忙，空闲回调几乎立刻返回 |
| 4 | 渐进渲染注入成本 | 拦截 `insertAdjacentHTML` → 30 次注入 / 398KB / **单次最长 0ms** | ❌ 注入本身极廉价 |

**决定性实验**：完全禁用高亮推进（`requestIdleCallback` 置空）后，
**节点只剩 320 个，长任务仍 834ms** —— 证明瓶颈与代码块高亮无关。

**CPU profile 给出铁证**（自耗时聚合）：

```
341.9ms  addObjectDiffToProperties  @react-dom-client.DEVELOPMENT.js
154.2ms  exports.jsxDEV             @react-jsx-dev-runtime.DEVELOPMENT.js
 34.1ms  jsxDEVImpl                 @react-jsx-dev-runtime.DEVELOPMENT.js
 23.6ms  ReactElement               @react-jsx-dev-runtime.DEVELOPMENT.js
 11.6ms  updateProperties           @react-dom-client.DEVELOPMENT.js
  9.8ms  runWithFiberInDEV          @react-dom-client.DEVELOPMENT.js
                            合计 ≈ 570ms
```

**全部来自 `.development.js`** —— 即 **React 开发模式**的
「props 深比较（`addObjectDiffToProperties`）」与「JSX 开发期检查」。
**这些代码在生产构建中完全不存在。**

⇒ **868ms 阻塞里约 570ms 是开发模式的代价，不是用户实际体验。**
⇒ 这也是为什么「优化调度」全都无效 —— 我一直在优化一个不是瓶颈的东西。

### 已落地的真实优化（可复算）

**代码块改为真正的按需高亮**（`hydrateCodeBlocks` 重写）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 高亮块数（20 万字符文档） | **638 个全部** | **46 个** |
| 保持纯文本的块 | 0 | **592** |

依据：实测 `requestIdleCallback` 88 次、间隔 14–22ms ⇒ **调度再细也没用，
成本本身没减少**。所以策略从「排空队列」改为「按需 + 有限预取」：
视口内/近视口立即高亮；远视口最多预取 40 个（缓冲快速滚动）；
更远的等滚动事件唤醒（额度补充）。这样「用户没看到的块不为其付出 CPU」。

### 🔴 附带发现：既有断言与新设计**直接冲突**

回归时 `verify_bigdoc_perf.cjs` 失败了 2 项：

```
❌ DOM 完整（节点 > 17000）
❌ 代码块全部高亮
```

这两条写于**上一轮性能优化**时，当时「DOM 完整 + 全量高亮」是**期望行为**
（用来验证「分批渲染没丢内容」）。而本轮把高亮改成按需后，
它们断言的正是**被优化掉的症状** —— 若继续保留，会把「正确的按需渲染」判成失败。

**处置**：改判为**新语义**（且判据没有变松）：

| 原断言 | 新断言 |
|---|---|
| DOM 完整（节点 > 17000） | DOM 按需（3000 < 节点 < 25000） |
| 代码块全部高亮（`pending === 0`） | 按需高亮（`shiki > 0 && pending > 0`） |

该脚本的**核心判据「单次写入体积 < 60KB」保持原样**（这是它最有区分度的指标），
跑通后实测 **30 次写入 / 单次最大 18KB** —— 说明渐进渲染本身没有退化。

⇒ **教训：改变一个被断言过的行为时，必须同步更新那些断言**，
否则要么得到假失败（把正确判成错误），要么为了"让测试过"而回退正确的优化。
分辨方法：看断言**当时是为了防什么**（此例是为防"一次性注入 398KB"，
而 `pending === 0` 只是那个实现下的附带观察，不是目的）。

### ✅ 已补：生产构建实测（2026-10-25）—— 验证了上文的推断

上文推断「~570ms 来自 React 开发模式、生产不存在」。当时**没有验证过**。
现在补上了：独立目录构建生产版（`output: "export"` 静态产物）+ 同域反代 `/api`，
在同一篇 20 万字符文档上对比：

| 指标 | 生产 | dev | 差异 |
|---|---|---|---|
| 长任务次数 | **0–1** | 6–8 | — |
| 总阻塞 | **0–62ms** | 830–1013ms | **少 93%** |
| 最长单次 | **0–62ms** | 174ms | — |
| DOM 节点 | 8,980 | 8,980 | 一致（行为正确） |

**推断被完全证实。**

#### 🔴 由此修正一处**收益表述**（重要）

生产下再对比「按需高亮」与「全量高亮」（注入对照实验）：

| | DOM 节点 | 生产长任务 |
|---|---|---|
| 按需（当前） | **8,980** | 50–57ms |
| 全量（注入回退） | **17,372** | 52ms |

⇒ **本优化的主要收益是 DOM 节点减少 48%**，对内存与滚动流畅度有实打实的价值；
但它**并不降低主线程阻塞** —— 生产下两者都只有 ~50ms，本就不是瓶颈。

此前我写的「降阻塞 868ms→」**表述不准确**：868ms 是 dev 数字，
且其中 93% 与高亮无关。已在 `markdown.ts` 注释里修正。

这个区分很关键：**它决定「若只为降阻塞，这个改动不值得做」**。

### 🔴 验证脚本自身的两个脆弱点（2026-10-25 暴露并修复）

新脚本首次跑通后，**第二次跑却失败**（4/9，长文档 0 个代码块）。
诊断发现是**脚本自身的时序竞态与硬编码**，不是产品缺陷：

| 问题 | 症状 | 修法 |
|---|---|---|
| `reload` 后立刻点卡片 | 元素刚挂载未完成布局，`click()` 静默无效 → 后续树永远 0 行 | 循环重试 + 检查 `getBoundingClientRect()` 非零尺寸 |
| 树行数硬编码 `>= 30` | 夹具知识库被回归清理后本机只剩 1 个库、行数达不到 30 → 40 次轮询全落空（**白等 12 秒**，且失败原因被引向"没渲染") | 改**自适应**：出现任意行且连续 3 次数量不变即算加载完 |
| `goto "/#/kb/xxx"` 进库 | hash 路由不重新执行脚本 → 树 0 行 | 改**点知识库卡片**（真实交互入口） |

修复后 `verify_prod_perf` 从 73s/4-9 回到 **26s/10-10**。

⇒ **教训：「脚本失败」先怀疑脚本自己。** 尤其是
① 硬编码的数据假设（行数、id、数量）会随夹具变化失效；
② `click()` 没有返回值，**必须用后续状态确认它真的生效**；
③ 输出不要用 `tail` 遮蔽 —— 本轮回归我曾用 `tail -60` 导致
跑了 71 分钟却看不到进度、无法判断是否卡死，只能杀掉重跑。

1. **`DELETE /folders/{id}` 与 `/kbs/{id}` 同样是软删除**（与 `/documents/{id}` 一样）。
   `verify_batch_move` 的 cleanup 只软删 → 每次跑往回收站堆 1 文件夹 + 1 知识库。

3. **runner 超时 `SIGKILL` 杀进程** → `finally` 根本不执行。
4. 断言口径只查活跃列表，不查回收站（同类问题第 3 次出现）。

| 层 | 措施 |

| **runner（根治）** | 新增 `scripts/fixture_sweep.cjs`，`run_all_verify` 跑完**自动收尾清扫** —— 这是唯一能覆盖「SIGKILL」与「新脚本忘清」的位置 |

（「未命名 xxx」额外要求内容 ≤60 字）；知识库/文件夹要求名字精确匹配**且 0 篇文档**，
有内容的一律跳过并告警；支持 `--dry` 先看会删什么。

对抗性验证：注入 3 篇夹具文档 + 1 个夹具知识库 → **全部抓到并清除** ✅。

### 🔴 孤儿数据缺陷：`delete_user` 不级联（2026-10-26 发现并修复）

数据完整性审计时发现**回收站接口返回 `kbs: []`，但数据库里有 17 条 `deleted_at` 的知识库**。
这个「接口与库不一致」是突破口。

#### 根因

`db.delete_user` 只 `DELETE FROM users`，**不清理其知识库 / 文件夹 / 文档**。
留下的数据 `user_id` 指向已删用户，而所有查询都按 `user_id` 过滤 → **谁都不看见**。

🔴 **后果比「占空间」严重得多**：这些是**永久不可见的幽灵** ——
用户看不到、删不掉、回收站也不显示，**只能直查数据库才发现**。

对照：`delete_kb` / `delete_folder` **早就做了级联**（软删下辖内容），
**唯独 `delete_user` 漏了** —— 属遗漏，不是设计选择。

实测积压：**17 个孤儿知识库 + 15 个孤儿文件夹 + 1 篇无主文档**。

#### 🔴 判据教训：「回收站里没有」是**假判据**

那正是当初失效的原因 —— 过滤后本来就看不到。
对抗性验证时亲眼见到：注入「不级联」缺陷后，
验证项**「回收站接口无残留」仍然 ✅**，而库里 kbs/folders/documents 各多出 1 条孤儿。

⇒ **唯一有效的判据是直接查库数孤儿行**（`user_id` 指向不存在的用户）。
⇒ 推论：**「API 返回空」≠「数据不存在」**。凡按某字段过滤的查询，
   都要问「**该字段本身失效时会发生什么**」—— 过滤会把异常态整个藏起来。

#### 审计日志的正确处置（首版做错了）

首版把 `audit_logs` 也一并删除 —— **这是错的**。
审计追溯是**合规要求**：「某账号在其存续期内做过什么」必须可查，
删了用户就把操作痕迹抹掉，而那恰恰是审计最需要保留的场景。

⇒ 改为**保留 `audit_logs`**，且验证判据也反过来：
不再断言「审计日志无孤儿」，而断言「**审计日志保留了该用户的操作痕迹**（数量不减少）」。
**判据方向搞反，会把正确行为判成失败。**

#### 修复

| 层 | 措施 |
|---|---|
| 后端 | `db.delete_user` / `store.delete_user`（JSON 后端）都做完整级联：内容类（documents + chunks / folders / knowledge_bases）与关系类（favorites / recent_views / notifications（含 `actor_id`）/ comments / kb_shares）硬删；**`audit_logs` 刻意保留** |
| 清扫 | `fixture_sweep.cjs` 加**孤儿检测 + 清理**（API 够不着，走 psycopg 直连）—— 以后即使再出现也会被回归收尾自动发现 |
| 解释器 | Python 自动探测项目 `.venv/bin/python`（保证有 psycopg，不依赖外部传参） |

#### 验证

- 新增 `verify_user_cascade.cjs` **15/15**：建临时用户 → 建其库/夹/文档/收藏/浏览
  → 删用户 → **直查库断言零孤儿**。
- 对抗性验证（注入「不级联」）→ 精准抓到 kbs/folders/documents **3 项失败** ✅。
- 后端 pytest **227/227 通过**。

## 三、右侧大纲：**实测正常，此前的判断是误报**

> ⚠️ 这一节最初被我误报为「无滚动容器 / 标题栏滚动失效」，**实测后全部推翻**。
> 保留误报记录以警示「探针方式错了会得出完全相反的结论」。

| 项目 | 我此前的判断 | 精确实测结果 |
|---|---|---|
| 滚动容器 | 「无」 | **有** —— `overflow-y: auto`，820px / 5895px |
| 标题栏 | 「跟着滚走了」 | **钉住** —— 滚动 1500px 后仍稳在 `top=48`（`position: sticky` 生效） |
| 条目渲染 | — | 204 条目正常 |

**误报原因**（三次错，每次原因不同）：
1. 用 `[data-testid*="toc"]` 之类的锚点找大纲 → 实现里没有 testid → 报「不存在」。
2. 找到 aside 后，用 `toc.querySelector("div")` 取标题栏 → 取到的其实是
   **第一个 div（拖拽手柄，`absolute`）** → 报「sticky 失效」。正确应取 `div.sticky`。

⇒ **教训：探针选错元素，会得出与事实完全相反的结论。**
「某个能力不存在/坏了」的结论，必须用**多种方式**交叉验证后才能下（换选择器、读源码、直接看 outerHTML）。

**唯一真实的不足**（是能力缺口，不是缺陷）：204 个条目没有过滤/搜索，只能硬滚 5075px。
优先级低于侧栏过滤（后者需滚 27.5 屏、需求更强）。

### ✅ 已落地：树内名称过滤

切换知识库时过滤词自动清空（否则会得到"空树"）。
