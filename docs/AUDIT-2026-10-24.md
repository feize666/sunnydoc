## 二、🔴 最高优先级：超长文档渲染阻塞

### 实测（Playwright，真实点击文档树打开）

```
DOM 节点          17,372
正文文本          181,999 字符
内容高度          232,988px（≈233 米）
长任务            7 次
主线程总阻塞       868ms
最长单次阻塞       275ms
代码块 638 个      → 3.0 秒内全部高亮，而首屏可见 0 个
```

### DOM 增长曲线（证明「渐进渲染有效，但总成本没降」）

```
  2330ms    320 节点    24 代码块   ← 首屏
  2523ms   1759 节点   127 代码块   ← 100 块/批推进中
  3001ms   8614 节点   638 代码块   ← 638 个代码块已全部高亮完
  3602ms  11473 节点   638 代码块   ← 但 DOM 还在长
  4803ms  17372 节点   638 代码块   ← 才稳定
```

**判读**：已有渐进渲染（`renderProgressively`，100 块/批 + `requestIdleCallback`）
是**正确且生效**的 —— 节点确实分批增长。但它只把阻塞**摊开**，没有降低**总成本**：
最终仍渲染全部 17,372 节点，且 **638 个代码块在 3 秒内就被全部 shiki 高亮，
而首屏可见的代码块数是 0** —— 也就是说**绝大部分高亮是白做的**。

长任务集中在 4.2s 之后（275 / 86 / 126 / 92 / 99 / 93 / 102 ms），
说明瓶颈在**批次的样式计算与布局**，不在 JS 解析。

### 🔴 根因追查（4 轮实测，最终定位到 CPU profile）

| 轮次 | 假设 | 实测结果 | 结论 |
|---|---|---|---|
| 1 | 代码块全量高亮是主因 | 改「近视口优先」排序 → 638 块仍 3.6s 内全高亮 | ❌ 无效 |
| 2 | `offsetTop` 坐标系算错 | 改用 `getBoundingClientRect` → 仍无效 | 修正了 bug，但**不是主因** |
| 3 | 调度频率不够 | 加 `requestIdleCallback` 埋点 → **88 次调用、间隔仅 14–22ms** | ❌ 浏览器不忙，空闲回调几乎立刻返回 |
| 4 | 渐进渲染注入成本 | 拦截 `insertAdjacentHTML` → 30 次注入 / 398KB / **单次最长 0ms** | ❌ 注入本身极廉价 |

**决定性实验**：完全禁用高亮推进（`requestIdleCallback` 置空）后，
**节点只剩 320 个，长任务仍 834ms** —— 证明瓶颈与代码块高亮无关。

**CPU profile 给出铁证**（自耗时聚合）：

```
341.9ms  addObjectDiffToProperties  @react-dom-client.DEVELOPMENT.js
154.2ms  exports.jsxDEV             @react-jsx-dev-runtime.DEVELOPMENT.js
 34.1ms  jsxDEVImpl                 @react-jsx-dev-runtime.DEVELOPMENT.js
 23.6ms  ReactElement               @react-jsx-dev-runtime.DEVELOPMENT.js
 11.6ms  updateProperties           @react-dom-client.DEVELOPMENT.js
  9.8ms  runWithFiberInDEV          @react-dom-client.DEVELOPMENT.js
                            合计 ≈ 570ms
```

**全部来自 `.development.js`** —— 即 **React 开发模式**的
「props 深比较（`addObjectDiffToProperties`）」与「JSX 开发期检查」。
**这些代码在生产构建中完全不存在。**

⇒ **868ms 阻塞里约 570ms 是开发模式的代价，不是用户实际体验。**
⇒ 这也是为什么「优化调度」全都无效 —— 我一直在优化一个不是瓶颈的东西。

### 已落地的真实优化（可复算）

**代码块改为真正的按需高亮**（`hydrateCodeBlocks` 重写）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 高亮块数（20 万字符文档） | **638 个全部** | **46 个** |
| 保持纯文本的块 | 0 | **592** |

依据：实测 `requestIdleCallback` 88 次、间隔 14–22ms ⇒ **调度再细也没用，
成本本身没减少**。所以策略从「排空队列」改为「按需 + 有限预取」：
视口内/近视口立即高亮；远视口最多预取 40 个（缓冲快速滚动）；
更远的等滚动事件唤醒（额度补充）。这样「用户没看到的块不为其付出 CPU」。

### 🔴 附带发现：既有断言与新设计**直接冲突**

回归时 `verify_bigdoc_perf.cjs` 失败了 2 项：

```
❌ DOM 完整（节点 > 17000）
❌ 代码块全部高亮
```

这两条写于**上一轮性能优化**时，当时「DOM 完整 + 全量高亮」是**期望行为**
（用来验证「分批渲染没丢内容」）。而本轮把高亮改成按需后，
它们断言的正是**被优化掉的症状** —— 若继续保留，会把「正确的按需渲染」判成失败。

**处置**：改判为**新语义**（且判据没有变松）：

| 原断言 | 新断言 |
|---|---|
| DOM 完整（节点 > 17000） | DOM 按需（3000 < 节点 < 25000） |
| 代码块全部高亮（`pending === 0`） | 按需高亮（`shiki > 0 && pending > 0`） |

该脚本的**核心判据「单次写入体积 < 60KB」保持原样**（这是它最有区分度的指标），
跑通后实测 **30 次写入 / 单次最大 18KB** —— 说明渐进渲染本身没有退化。

⇒ **教训：改变一个被断言过的行为时，必须同步更新那些断言**，
否则要么得到假失败（把正确判成错误），要么为了"让测试过"而回退正确的优化。
分辨方法：看断言**当时是为了防什么**（此例是为防"一次性注入 398KB"，
而 `pending === 0` 只是那个实现下的附带观察，不是目的）。

### ⚠️ 尚未解决 / 需要决策

1. **`17,372` 个 DOM 节点是真实存在的**（与 React 模式无关）。
   要真正压下来需要**虚拟滚动**（只渲染视口附近的内容），
   但这会改动预览渲染管线，且与「全文搜索命中定位」「大纲 scroll-spy」
   「导出」都有耦合 —— **属架构级改动，代价高，需要单独评估**。

## 三、右侧大纲：**实测正常，此前的判断是误报**

> ⚠️ 这一节最初被我误报为「无滚动容器 / 标题栏滚动失效」，**实测后全部推翻**。
> 保留误报记录以警示「探针方式错了会得出完全相反的结论」。

| 项目 | 我此前的判断 | 精确实测结果 |
|---|---|---|
| 滚动容器 | 「无」 | **有** —— `overflow-y: auto`，820px / 5895px |
| 标题栏 | 「跟着滚走了」 | **钉住** —— 滚动 1500px 后仍稳在 `top=48`（`position: sticky` 生效） |
| 条目渲染 | — | 204 条目正常 |

**误报原因**（三次错，每次原因不同）：
1. 用 `[data-testid*="toc"]` 之类的锚点找大纲 → 实现里没有 testid → 报「不存在」。
2. 找到 aside 后，用 `toc.querySelector("div")` 取标题栏 → 取到的其实是
   **第一个 div（拖拽手柄，`absolute`）** → 报「sticky 失效」。正确应取 `div.sticky`。

⇒ **教训：探针选错元素，会得出与事实完全相反的结论。**
「某个能力不存在/坏了」的结论，必须用**多种方式**交叉验证后才能下（换选择器、读源码、直接看 outerHTML）。

**唯一真实的不足**（是能力缺口，不是缺陷）：204 个条目没有过滤/搜索，只能硬滚 5075px。
优先级低于侧栏过滤（后者需滚 27.5 屏、需求更强）。

## 四、侧栏浏览效率

### 实测

```
树行总数          432（文件夹 13 / 文档 419）
内容高度          14,702px
可视高度          534px
⇒ 需滚动          27.5 屏
根层文件夹        55 个
```

**问题**：55 个根层文件夹 + 419 篇文档，要滚 27.5 屏才能看到底部；
纯靠滚动很难找到目标，而全文搜索（`/api/v1/search`）只覆盖**文档内容**、
只返前 50 条、且会切到**独立的结果视图** ——
「我知道它叫什么，帮我找出来」这个场景它并不合适。

### ✅ 已落地：树内名称过滤

新增 `data-testid="tree-filter"` 输入框（条目 > 12 时才显示），纯前端过滤、零网络请求：

| 筛选词 | 结果 | 自动展开 |
|---|---|---|
| `openEuler` | 命中目标文档，视口内可见 | ✅ |
| `05-安全` | 5 行（3 文档 + 2 文件夹，**保留祖先链**） | ✅ |
| `K8S` | 25 行（19 文档 + 6 文件夹） | ✅ |
| `zzz不存在` | 0 行 + 明确空态提示 | — |
| 清空 | 恢复 432 行（无副作用） | — |

**两条关键语义**：
- **保留命中项的祖先链** —— 否则用户看到一条孤立文档，不知道它在哪个目录下。
- **目录自身命中时保留整棵子树** —— 搜目录名即看其全部内容，而不是只剩一个空壳目录。

另外：过滤态**强制展开命中路径**（否则「搜到了却藏在折叠目录里」等于没搜），
且**不污染用户原有的展开偏好**（清空关键词后回到原状态）。
切换知识库时过滤词自动清空（否则会得到"空树"）。
